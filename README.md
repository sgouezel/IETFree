# Almost Every Pair of Interval Exchange Transformations Does Not Generate a Free Group
### A Lean 4 formalization

This repository contains a formalization in Lean 4 of the paper

> Sébastien Gouëzel, *Almost every pair of interval exchange transformations does not generate a
> free group*, [arXiv:2610.29993](https://arxiv.org/abs/2610.29993) [math.DS], 2026.

The paper's abstract: *"We show that the Lebesgue measure of the set of pairs of interval exchange
transformations that generate a free group of rank 2 is zero."*

The formalization was produced by **autoformalization**: an AI agent working in **SAIR Open Math
OS**, writing Lean against a pinned Mathlib and checking every step by compilation. The agent's
development ledger — what was tried, what failed, which statements had to be restated and why — is
[`NOTES.md`](NOTES.md); it is a log, not a specification.

**Status.** Everything in `IETFree/` is proved, and the appendix `IETFree/Check.lean`
prints an axiom report of 296 `#print axioms` lines, all of them
`[propext, Classical.choice, Quot.sound]` except the one pure-group lemma
[`commutatorElement_inv_inv_eq_one_iff`](https://github.com/sgouezel/IETFree/blob/main/IETFree/MeasureTools.lean#L212), which needs only `propext`. The main theorem is proved
**conditionally on two results from the literature**, which are stated as `Prop`s and taken as
hypotheses, never as axioms — see [Limitations](#limitations-the-two-inputs-from-the-literature).
The six `sorry`s in the tree are all deliberate placeholder *statements*, three in each of the two
statement files: the *display-only* `Challenge.lean` (nothing imports it: the definition hole
[`mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/Challenge.lean#L69), [`coe_mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/Challenge.lean#L75) and the unconditional [`main`](https://github.com/sgouezel/IETFree/blob/main/Challenge.lean#L101)) and the comparator challenge
`ChallengeWeak.lean` (the hole [`mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L99), [`coe_mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L108) and [`main`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L186) with the two hypotheses), which
`IETFree/ChallengeWeakSolved.lean` proves and fills — it is the comparator's *solution*; see
[the comparator challenge](#the-comparator-challenge).
(`Tasks/` holds the statement files that seeded the AI proof search; they are not library code, and
`Build.sh` compiles only `Tasks/Match.lean`, which checks that those statements still agree with the
library.)

Requirements: Lean 4.33.1. The repository is a **Lake project**: `lean-toolchain` (Lean 4.33.1),
`lakefile.toml` (Mathlib pinned at the `v4.33.1` tag, and one Lean library for `IETFree/` plus one for
each of the two statement files) and `lake-manifest.json`. The build is

```sh
lake exe cache get   # once: download Mathlib's oleans
lake build           # build IETFree, Challenge and ChallengeWeak
```

`Build.sh` is the same compilation without Lake — the same modules, in the same order, with the same
options — which is what this development VM needs, `/opt/mathlib` being a root-owned, read-only,
prebuilt Mathlib that Lake cannot use as a package there; it additionally prints the axiom report and
the sorry count and runs the comparator check. The import list of the root module `IETFree.lean` is
generated by `lake exe mk_all --lib IETFree`, so a new module is added to it by that command and not by
hand.

Both builds enable the Mathlib linter set (as `lakefile.toml` does) and are **warning-free**: a clean
`lake build` reports no linter warnings at all, and neither does `./Build.sh`. The only diagnostics are
the six `sorry`s of the two statement files, which `Build.sh` counts.

The *declaration* linters (Mathlib's lint driver, which `lake build` does not run) are clean as well:
`lake exe runLinter IETFree` passes on all 982 declarations of the library, and so does the same
command on `Challenge` and `ChallengeWeak`. In this VM the driver's executable cannot be built (its C
objects would go into the read-only Mathlib tree), so it is run interpreted — the recipe is in
`NOTES.md`, §"The declaration linters are clean".

```sh
./Build.sh                             # plain-`lean` build, axiom report, sorry count (~2 min)
./Build.sh --strict                    # additionally fail if `sorryAx` is reachable from Check.lean
MATHLIB=/opt/mathlib Comparator/run.sh # the genuine comparator end to end (drop MATHLIB if lake
                                       # resolves Mathlib itself; see the section below)
```

## What is proved

The final statement is [`main`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L332) (`IETFree/ChallengeWeakSolved.lean:332`), in the words of the challenge
file:

```lean
theorem main (hMV : MasurVeechFun) (hVR : VeechRigidityFun) {d e : ℕ} [NeZero d] [NeZero e]
    (π : Equiv.Perm (Fin d)) (σ : Equiv.Perm (Fin e)) :
    ∀ᵐ p ∂((simplexVolume d).prod (simplexVolume e)),
    ∃ w : FreeGroup (Fin 2), w ≠ 1 ∧
      evalWordEquiv w (mkIETEquiv p.1 π 0) (mkIETEquiv p.2 σ 0) = 1
```

which is Theorem 1.1 of the paper, with its two external inputs made explicit — here in the form of
[`MasurVeechFun`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L100) and [`VeechRigidityFun`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L106), the paper's hypotheses for the *map* [`mkIETFun λ π 0`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L562). The
library's own form, [`main_of_library`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L281) (`IETFree/ChallengeWeakSolved.lean:281`), is the same statement
with [`MasurVeech`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L58) and [`VeechRigidity`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L65), which are stated for the exchange [`mkIET1 λ π h : IET 0 1`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L1013);
the two forms agree ([`IET.pow_apply_iterate`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L1003)). `Challenge.lean` states the
unconditional-looking Theorem 1.1 in Mathlib-only language.

## The comparator challenge

[Comparator](https://github.com/leanprover/comparator) is Lean FRO's independent judge for a Lean
proof: given a *challenge* file that states a theorem with `sorry` and a *solution* file that proves
it, it checks that the solution proves the same statement, uses no axiom outside a permitted list,
and that the kernel accepts the proof. (Comparator is deprecated upstream: as of Lean v4.35.0 it is
part of core, as `lake comparator` with `lake check`. This library is pinned to Lean 4.33.1, so the
standalone tool is the one that applies.)

The goal of the challenge is `ChallengeWeak.lean` — Theorem 1.1 with Masur–Veech and Veech's
rigidity as hypotheses — and the solution is **the library itself**:

| file | contents |
|---|---|
| `comparator.json` | the configuration: challenge module, solution module, the theorem targets, the definition hole, `permitted_axioms` |
| `ChallengeWeak.lean` | the challenge: one self-contained file, `import Mathlib` only |
| `IETFree/ChallengeWeakSolved.lean` | the solution: imports the library, proves both targets and fills the definition hole |

```json
{
  "challenge_module": "ChallengeWeak",
  "solution_module": "IETFree.ChallengeWeakSolved",
  "theorem_names": ["coe_mkIETEquiv", "main"],
  "definition_names": ["mkIETEquiv"],
  "permitted_axioms": ["propext", "Quot.sound", "Classical.choice"]
}
```

Comparator compares the two statements declaration by declaration, by name, and then every
declaration they reach; only the targets ([`coe_mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L621), [`main`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L332)) and the definition hole
([`mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L605)) may differ. So the challenge declares, verbatim, the declarations its statement uses
([`leftEnd`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L271), [`idx`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L361), [`mkIETFun`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L562), [`simplexVolume`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L232), [`unitMeas`](https://github.com/sgouezel/IETFree/blob/main/IETFree/MeasureTools.lean#L24), [`evalWordEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L56), …; the last of these is not
a library tool but the bridge to the statement, and it is declared in `IETFree/ChallengeWeakSolved.lean`),
renames the ones
that cannot be the library's ([`UniqueErgodicFun`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L137), [`IsRigidByTranslationsFun`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L143), [`MasurVeechFun`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L100),
[`VeechRigidityFun`](https://github.com/sgouezel/IETFree/blob/main/ChallengeWeak.lean#L167) — the library's [`UniqueErgodic`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L30) and [`IsRigidByTranslations`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L36) are stated for
[`f : IET 0 1`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L947)), and leaves [`mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L605) a *definition hole*, pinned down by the target
[`coe_mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L621). [Comparator/README.md](Comparator/README.md) has the details, including why the hole
is needed: the library proves the two inverse laws of [`mkIETEquiv`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L605) through a `private` core, whose name
cannot exist in another module.

### Reproducing it

```sh
./Comparator/run.sh                        # a machine where lake resolves Mathlib itself
MATHLIB=/opt/mathlib ./Comparator/run.sh   # this VM: prebuilt, read-only Mathlib
```

`Comparator/run.sh` is the whole recipe in one command: it fetches and builds the two tools (comparator
at `3927ad3`, the last revision on a Lean v4.33 toolchain, with `lean4export` at its `v4.33.0` tag),
builds `ChallengeWeak` and `IETFree.ChallengeWeakSolved` with Lake (in a project that requires Mathlib by
path when `MATHLIB` is set — on a machine where `lake exe cache get` has been run, the repository's own
Lake project already has both as targets), exports both modules and runs the comparison. It uses `landrun` if it is on `PATH` and the
repository's `fake-landrun.sh` otherwise (`landrun` is not installed here), and it exits 0 only if the
pair is accepted. On this tree it printed

```text
Lean default kernel accepts the solution
Your solution is okay!
```

and it is not vacuous: with `w ≠ 1` changed to `w = 1` in the challenge's [`main`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ChallengeWeakSolved.lean#L332), the same run fails
with `Challenge and solution theorem statement do not match: 'main'`.
[Comparator/README.md](Comparator/README.md) explains each step.

`Comparator/Check.lean` is the cheap guard that `./Build.sh` runs on every build: it applies the
comparator's own algorithm to the two compiled modules, and the build fails if it does not pass; it
compares 32 661 declarations and finds no difference.

## Limitations: the two inputs from the literature

Two results are used and **not** proved here. Both are classical theorems about interval exchange
transformations; the paper cites both to Veech's *Metric theory of interval exchange transformations
I* (Amer. J. Math. 106 (1984) 1331–1359). The formalization states each as a `Prop` — a *hypothesis*
of the theorems that need it, so it never appears in `#print axioms`.

| literature | in the paper | in Lean |
|---|---|---|
| **Unique ergodicity.** For every irreducible permutation of `d ≥ 2` cells, Lebesgue-almost every length vector gives a uniquely ergodic exchange — H. Masur, *Interval exchange transformations and measured foliations*, Ann. of Math. 115 (1982) 169–200, and W. A. Veech, *Gauss measures for transformations on the space of interval exchange maps*, Ann. of Math. 115 (1982) 201–242; the paper cites Veech, *Metric theory I*, **Theorem 1.2**, in the paragraph following Definition 2.1 | the property "almost every `f_{π,λ}` is uniquely ergodic"; used in the a.e. transfer of Lemma 3.4 ([`ae_blockGood_free`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockData.lean#L242)), where Theorem 2.6 is applied to the rescaled block | [`MasurVeech`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L58) (`IETFree/Irreducible.lean:58`): `∀ (d) (_ : 2 ≤ d) [NeZero d] (π), IsIrreduciblePerm π → ∀ᵐ lam ∂(simplexVolume d), ∀ (h : lam ∈ simplex d), UniqueErgodic (mkIET1 lam π h)` |
| **Rigidity by translations.** For every irreducible permutation, Lebesgue-almost every length vector gives an exchange that is rigid by translations — Veech, *Metric theory I*, **Theorem 1.4**, from which the paper derives **Proposition 2.4** | Proposition 2.4 (Section 2), and the same a.e. statement for the rescaled block in Lemma 3.4 | [`VeechRigidity`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L65) (`IETFree/Irreducible.lean:65`): the same shape, with [`IsRigidByTranslations (mkIET1 lam π h)`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L36) in place of [`UniqueErgodic`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L30) |

Everything else in the paper is proved, including Proposition 2.5 (almost every pair is Diophantine),
which is a consequence of the easy direction of Khintchine–Groshev and is formalized as
[`ae_diophantine`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Diophantine.lean#L1013) (`IETFree/Diophantine.lean:1013`).

Two further remarks on the scope of the formalization:

* [`MasurVeech`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L58) carries the hypothesis `2 ≤ d`. On a single cell the exchange is the identity for
  every length vector, and the identity is not uniquely ergodic, so the restriction is necessary;
  [`VeechRigidity`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L65) does not need it (the identity is rigid by translations).
* Lemma 1.2 of the paper (an irrational rotation and an exchange do not generate a free group) is an
  illustration in the introduction and is **not** part of this development; nor is the remark
  following Theorem 1.1 (that the set of pairs is, in fact, open and of full measure).

## Discrepancies with the paper, and why the formalization departs from it

None of these changes a statement of the paper; each is a deliberate choice of *form*, made where the
paper's prose leaves room and where the formal version is markedly easier to prove. Two of them are
statements that had to be pinned down because the first formal reading turned out to be **false**;
both were found by machine-checked counterexamples, and both were repaired towards the paper's
meaning.

**1. Open regions instead of connected components of a hyperplane complement.**
The paper fixes a connected component `O` of the complement of the finitely many hyperplanes
`k + Σ a_i λ_i + Σ b_j μ_j = 0` (with integer coefficients bounded by 4), on which the combinatorics
of `gf` is constant, and argues inside it. The formalization instead defines a [`GoodRegion`](https://github.com/sgouezel/IETFree/blob/main/IETFree/GoodRegion.lean#L1088) as an
*open ball* around a good parameter ([`exists_compPresentation_on_ball`](https://github.com/sgouezel/IETFree/blob/main/IETFree/GoodRegion.lean#L879)), on which one fixed list `s`,
one fixed permutation `ρ` and one fixed combinatorial type are known to present `gf`, and then covers
the almost-everywhere statement by a *countable* family of such balls
([`exists_countable_goodRegion_cover`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockEndpoints.lean#L321)) and `MeasureTheory.ae_all_iff`. What the paper obtains from
connectedness, the formalization obtains from continuity and compactness-free openness: no connected
component, no hyperplane, and — importantly for everything downstream — no *global* monotonicity of
the singularity list, only the pointwise form `G.cellLen hq = compLenVec G.s q (monoAt G hq)`. This is
why no preconnectedness or convexity hypothesis appears anywhere in the final development.

**2. Bad parameters through the Diophantine condition, not through hyperplanes.**
Relatedly, the paper's "except on finitely many hyperplanes" becomes `¬ IsBadParam q`
(i.e. `q ∈ goodParams`: no small integer relation `k + Σ a_i v_i + Σ b_j w_j = 0` between the free
coordinates), whose null set is proved with the same Khintchine–Groshev/Diophantine machinery as
Proposition 2.5 ([`ae_goodParams`](https://github.com/sgouezel/IETFree/blob/main/IETFree/ReductionData.lean#L801)). Reusing Proposition 2.5 is much cheaper than building a
measure-theory-of-hyperplanes API, and it gives the statement the proof actually needs (a bound, not
just nonvanishing).

**3. Explicit combinatorial data instead of "the combinatorics is constant".**
The paper says "the map `gf` is an interval exchange transformation with respect to a permutation `ρ`
which does not depend on the parameters in `O`". The formalization carries the combinatorial type as
explicit data: [`IsCompType lam π hl mu s a B`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Presentation.lean#L53) with a cut map `a : Fin (d+1) → Fin (n+1)` and a cell
map `B : Fin n → Fin e`, the singularity shape [`SingularityShape`](https://github.com/sgouezel/IETFree/blob/main/IETFree/GoodRegion.lean#L60), `ρ` as a field of [`GoodRegion`](https://github.com/sgouezel/IETFree/blob/main/IETFree/GoodRegion.lean#L1088), and
the *block* permutation as an explicit `Equiv.Perm (Fin (l - k))` ([`blockPerm π k hkl hln hstab`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockRescaling.lean#L403),
`ρ_b j = π (j+k) - k`). This is the single biggest simplification: every statement about the block is
then a statement about a concrete permutation, so the literature inputs — which quantify over
permutations — apply to it directly, with no transport along an existence statement.

**4. Lemma 3.2 stated intrinsically — and the first rendering of it was false.**
The paper concludes "the restriction to `P` of the permutation `ρ` is irreducible", i.e. that no
*proper initial piece* of the block is invariant. The first formal rendering said something weaker
and different: that no initial piece `[u, c)` is mapped into the **whole block** `[u, v)`. That is
**false** — it fails as soon as `E ∘ D` maps some `[u, c)` into `[u, v)` at all, which happens for
every pair on the block `[0, 1)` (the composition maps `[0, 1)` into itself) and, more generally,
whenever a good pair has no interior pair-splitting point. Machine-checked counterexample:
`d = e = 2`, both permutations the transposition, `λ = 1/3`, `μ = 1/4`. The repaired statement,
[`IsCompIrreducibleOn D E u v`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockIrreducibility.lean#L145), says exactly what the paper says (no invariant initial sub-block
`[u, c)` inside `[u, v)`), and [`irreduciblePerm_blockPerm`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockDatum.lean#L56) turns it into [`IsIrreduciblePerm`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L44) of
[`blockPerm`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockRescaling.lean#L403).

**5. The datum of "`gf` is an IET" had to be pinned down the same way.**
Our first [`IsCompPresentation`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Presentation.lean#L100) required `gf` to map the `i`-th marked cell *onto the `ρ i`-th cell of
the same list* — again false (for `λ = (1/3, 2/3)` and the transposition, `f 0 = 2/3` is not a cell
start). The corrected field is the standard IET datum: `gf` translates the `i`-th cell by
`listImageLeft ρ s i - listLeftEnd s i`. The images of the cells are a *different* interval partition
of `[0,1)`, placed according to `ρ`.

**6. Unique ergodicity in uniform Birkhoff form.**
Definition 2.1 says "the only invariant probability measure is Lebesgue"; [`UniqueErgodic f`](https://github.com/sgouezel/IETFree/blob/main/IETFree/Irreducible.lean#L30) says that
for every continuous `ψ` the Birkhoff averages converge to `∫ ψ d unitMeas` *uniformly on* `[0,1)`.
This is equivalent for these systems, and it is the form Lemmas 2.9 and 2.10 actually use (a
convergence statement with an explicit `N`). It is a strengthening, not a weakening: it gives more
than the paper's definition at the point of use.

**7. Almost-everywhere statements carry the simplex membership as a binder.**
Where the paper writes "there is a full measure subset `Ω ⊆ Δ_π × Δ_σ` such that, for `(λ,μ) ∈ Ω`,
…", the formalization writes `∀ᵐ λ ∂(simplexVolume d), ∀ (h : λ ∈ simplex d), …`. The two are
equivalent, and the binder gives the proof access to the membership of the point it is reasoning
about.

**8. The measure is the pushforward of Lebesgue measure on the free coordinates.**
[`simplexVolume d`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L232) is the image of Lebesgue measure on the region `{v | v > 0, Σ v < 1}` under
[`simplexMap d`](https://github.com/sgouezel/IETFree/blob/main/IETFree/IET.lean#L224), rather than Lebesgue measure on the simplex `Δ_π` itself. Since only null sets are
ever transported, no Jacobian appears anywhere; [`absolutelyContinuous_map_rescaleSub`](https://github.com/sgouezel/IETFree/blob/main/IETFree/SubintervalTransfer.lean#L514),
[`compLen_absolutelyContinuousAt`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockData.lean#L197) and [`absolutelyContinuous_map_blockFree`](https://github.com/sgouezel/IETFree/blob/main/IETFree/BlockAETransfer.lean#L182) are absolute-continuity
statements, which is exactly what the paper's "smooth with a derivative of maximal rank" step is used
for.

**9. The one-cell block is separated out.**
In Lemma 3.4 the paper splits `r = 1` (`gf` is the identity on the block, and the word `yx` works)
from `r ≥ 2` (where Theorem 2.6 applies to the rescaled pair). The formalization does the same, and
makes the split explicit: the hypothesis `2 ≤ l - k` is carried by the branch that applies Theorem 2.6
(at `l - k = 1` the rescaled length vector is identically `1` and the rescaled exchange is the
identity, which is not uniquely ergodic), and the one-cell block is handled by an explicit word
([`genX`](https://github.com/sgouezel/IETFree/blob/main/IETFree/MeasureTools.lean#L130) in Lemma 3.4, `genY * genX` when the single cell is a cell of `g`).

**10. Commutators are Mathlib's.**
The paper writes `[a, b] = a⁻¹b⁻¹ab`, putting the inverses on the left; the formalization uses
Mathlib's `⁅a, b⁆ = a * b * a⁻¹ * b⁻¹` (`commutatorElement`, with the inverses on the right), so the
paper's commutator is `⁅a⁻¹, b⁻¹⁆`. Most of the lemmas are true in either convention and are stated
with `⁅·,·⁆` — the combinatorial Lemma 2.7, the word-length bound, the evaluation of a commutator, and
the two assembly lemmas that make a commutator trivial on a union of invariant blocks. The one place
where the direction matters is the support estimate of Lemmas 2.8–2.10: the support of `[φ, ψ]` is
contained in `A ∪ φ⁻¹A ∪ ψ⁻¹A`, with `A` the intersection of the supports, and the measure of the
`ψ⁻¹` term is controlled by the unique ergodicity of `f` (with `ψ = f^q`). There the words are written
`⁅φ⁻¹, ψ⁻¹⁆`, which is the paper's commutator, and the proofs are unchanged. The two conventions
vanish together ([`commutatorElement_inv_inv_eq_one_iff`](https://github.com/sgouezel/IETFree/blob/main/IETFree/MeasureTools.lean#L212)), so no statement is weakened.
